# Change With Context

每项需求有可观察的完成条件，每处修改有需求和源码依据，每个受影响连接有处理结论。关系图用于定位候选；当前源码决定是否适配。默认复用项目已有检查，不要求建立新测试集。

## 触发门槛

只有以下情况才自动使用本技能：

- 用户明确点名本技能，或明确要求追踪影响范围、同步所有相关代码；
- 修改公共 HTTP/API 接口、消息事件、共享配置键、数据/存储格式、导出符号或生成源，且存在其他模块的消费者；
- 需求本身涉及两个或更多模块，或一个模块的修改会改变另一个模块可观察的输入、输出或行为。

以下修改默认按普通轻量编辑处理，不建立关系地图基线、`change.json` 或范围报告：单个模块内的局部配置值、路由内部常量、文档/注释、格式化、文案、测试夹具，以及已确认不改变共享契约的重命名或清理。仅仅“改配置”不足以触发本技能；只有配置键、结构或默认行为被多个模块消费时才算共享配置变化。

自动判断不确定时，先查看目标文件和直接引用；只有发现共享边界或第二个受影响模块后才进入本技能流程。技能已因用户显式点名而加载时，仍按用户指定范围执行。

## 入口与任务边界

- 先确定用户要求的项目、修改目标、需要保持的行为与完成条件，读取适用的 AGENTS.md。只在缺失信息会改变业务结果或违反用户明确限制时澄清；已授权的修改继续完成，不逐步请求确认。
- 用户只要求方案时输出影响清单与验证方式，到此结束。用户要求实施时执行下述流程；发现必要适配在用户明确禁止的范围内时，说明冲突并澄清该范围。
- 本技能依赖已安装的 `project-map`。先定位并读取其 SKILL.md。默认脚本在两技能同级目录寻找它，也可用 `--project-map-skill <目录>` 指定。缺失时说明依赖，不自行安装未知工具。
- `<skill>` 是本技能目录，`<map-skill>` 是 project-map 目录，`<root>` 是项目根。任务产物放在 `<root>/.agent-context/changes/<任务短名>/`，每个任务使用独立目录。用户指定其他位置时采用该位置，并从 project-map 快照中排除项目内的产物目录。所有路径含空格时加引号。

## 1. 核验地图与保留基线

读取地图的版本、覆盖范围与未知项；使用 project-map 的 `check` 检查快照。缺失或过期时，按该技能复核有关源码并更新地图；不能只重写哈希沿用旧关系。地图新鲜不代表依赖分析完整。

在修改业务源码前捕获基线：

```text
python <skill>/scripts/check_change.py capture --root <root> --map <root>/.agent-context --out <root>/.agent-context/changes/<任务短名>/baseline.json
```

基线包含文件哈希、地图快照 ID 和 Git 中已有改动的文件名，不保存源码或执行回滚。保存任务开始时有关文件的现有 diff，供最后复核已有修改。非 Git 项目以开始时的文件内容和用户提供的上下文为准。脚本拒绝覆盖基线；实施后不能重新捕获基线以掩盖本次变更。

## 2. 明确改变的符号或契约，形成影响清单

- 从需求识别参数、返回值、字段、事件、配置、存储格式或行为变化。文件级地图不能直接说明其中哪个符号受影响。
- 使用 project-map 查询依赖与使用者，阅读两端实现，并用项目已有语言工具或 `rg` 补充引用。箭头为“依赖方 → 被依赖方”；接口消费者到提供实现可能跨契约走两跳。按契约继续传播，遇到对外行为稳定且已核验的边界停止扩展，不固定查一跳，也不无条件遍历全图。
- 将有关文件分为必须修改（`modify`、`add`、`delete`）与核验后无需修改（`verify`），各附简短理由和源码位置。`confirmed` 仅表示关系存在，不能等同于必须修改；`inferred` 需要核实实际机制。
- 从用户需求及项目已有约定写可观察的完成条件和需要保留的行为。未知的仓库外消费者、动态注册或兼容策略记入 `unresolved`；若未知项决定所需业务结果，先澄清。无需让不影响本次修改的未知项阻塞任务。
- 按 [轻量变更协议](references/change-protocol.md) 写 `change.json`，向用户简要说明目标与预计影响。常规实施不等待额外批准。

## 3. 实施必要适配

逐项修改，保持现有风格，保护用户已有修改。生成代码优先修改其源定义并使用项目既有生成方式。不得因为修改某文件而顺便重构其中无关代码。

新增契约变化或发现遗漏时，核实新增影响并更新清单；理由不能只是“该文件已经改了”。实施后旧地图过期是正常情况：使用修改前保存的候选关系作为线索，结合当前源码与实际 diff 复核；旧证据行号可能移动，不对过期地图直接运行正式查询。

## 4. 轻量验证

- 从项目说明、包脚本与配置发现现有命令，执行适用的构建/编译与类型检查。没有独立命令时记录不适用及原因；一个命令覆盖两项时只执行一次并注明。不要为了本技能引入新构建工具。
- 按影响范围运行已有相关测试，不默认新建测试集。仅当本次实际行为无法通过编译、类型或已有检查观察时，做一项针对性运行验证。不要因普通修改扩展为全面审计或大量测试。
- 记录实际命令、结果及简短说明。失败时修复本次造成的问题；既有失败须有修改前记录或其他可靠证据，不能把新失败直接归为既有问题。检查对应最终源码；后续改动影响了检查内容时只重跑相关项。

执行范围校验：

```text
python <skill>/scripts/check_change.py check --baseline <root>/.agent-context/changes/<任务短名>/baseline.json --plan <root>/.agent-context/changes/<任务短名>/change.json --out <root>/.agent-context/changes/<任务短名>/scope-report.json
```

范围外文件、遗漏适配或操作类型不符都会使脚本返回非零。复核原因后修正本次修改或有依据地修正清单；仅撤销自己造成的改动，不自动恢复整份文件或覆盖用户修改。阅读最终 diff，检查同一文件内的无关改动、需求偏离、连接两端和已有修改是否保留。

脚本检查的是 project-map 清单覆盖的文件变化，不自动运行项目命令或判断业务语义。排除范围、用户已有改动的同文件合并以及外部变化需要源码/diff 复核；通过脚本不能证明绝无误改。

## 5. 刷新关系并交付

按 project-map 复核变化涉及的关系、证据位置与覆盖范围，更新分析后生成新快照和地图，保留旧任务基线。源代码未再次变化时不重复已通过的检查；地图等产物变化不要求重跑构建。

完成条件：需求完成，适用的构建/类型检查通过，相关检查无本次新增失败，范围异常已处理，地图反映最终源码。最终说明修改目的、有关模块的处理、验证结果及具体未验证边界。未完成或存在阻塞时如实报告，不用“全部通过”替代缺失检查。
